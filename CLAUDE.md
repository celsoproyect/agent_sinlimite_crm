# Project notes (Sin Limite IA CRM)

- **Language:** the owner works in Spanish. The UI is translated with next-intl (`messages/es.json`, `en.json`; Korean was removed); every new string goes into both. Spanish is the default; `LocaleSwitcher` (`src/components/layout/locale-switcher.tsx`) sits in the header and on the auth pages. Spanish labels run longer than English ones, so never rely on `whitespace-nowrap` inside fixed-width columns (the settings rail used to spill over its panel).
- **Timezone:** the business always runs in `America/Santo_Domingo`. Use the helpers in `src/lib/business-timezone.ts` (`businessToday`, `businessDate`, `businessTime`, `businessLocalToInstant`, …), never the host's or browser's local time. Tests run with `TZ=UTC`.
- **Verifying Supabase writes:** an update that RLS filters out returns no error and 0 rows. When a save must have happened, chain `.select()` and check the rows.
- **AI agent** (`src/lib/ai/`):
  - **Who owns what (migration 072):** the AI key is the platform's. The super admin pays for it and bills it in the plan (Super admin → IA de la plataforma, `platform_ai_config`, service role only, via `/api/super-admin/ai-platform`; `loadPlatformAiConfig` in `platform.ts`, cached 30s). `ai_configs.api_key` NULL = run on the platform key. Only a super admin can set an account's own key (trigger-guarded; Super admin → Cuentas y consumo → Editar agente, `/api/super-admin/accounts/[id]/ai`). Each account's owner/admin edits the agent itself (prompt, switches, handoff, lead pipeline, KB, FAQ) in Configuración → Agente de IA (`ai-config.tsx` + `agent-behaviour-form.tsx`, saved by `POST /api/ai/config` through `saveAgentSettings` in `agent-settings.ts`); that route never accepts keys. The account name stays in Super admin.
  - Monthly limit: `accounts.ai_monthly_limit` (NULL = no limit, super-admin only) caps the `ai_usage_log` runs per business month on the platform key. When it is reached, `loadAiConfig` returns null and the AI pauses. Own-key accounts are never capped. Embeddings fall back to the platform's key and model.
  - Channels: WhatsApp goes through `auto-reply.ts`, the web widget through `widget-reply.ts` (text only; booking behind the `widget_booking` module), and the inbox draft and the playground through `src/app/api/ai/*`. Both providers (`providers/openai.ts`, `providers/anthropic.ts`) declare the same tools, and the shared parsing lives in `providers/shared.ts`. A tool change has to touch both adapters.
  - Booking tools are only wired when `accounts.booking_settings.hours` is saved. Without them, the prompt forbids promising appointments.
  - `check_availability(date, time?)` returns `{ requested, slots }`. When the requested time is free, the agent books it right away; otherwise it offers the 3 nearest open slots, which can fall on other days.
  - Every booking needs the customer's full name and phone (`customer_name`/`customer_phone`, migration 062). The reference code is `CITA-` plus the first 6 hex digits of the booking id (`src/lib/bookings/reference.ts`), so it needs no column. WhatsApp BSUID contacts have no phone, which is why the agent asks for one.
  - Changes go through `find_appointments` (by phone, optionally the reference) → `check_availability` → `reschedule_appointment`, which moves the same row and resets its reminder sends. `cancel_appointment` cancels. The agent must never call `book_appointment` to change an appointment.
  - Knowledge base (`knowledge.ts`): semantic search needs chunk embeddings. Documents ingested before an embeddings key existed have none, so saving a new embeddings key or model re-embeds everything in the background (`reindexKnowledge`, via `after()` in `/api/ai/config`), and `/api/ai/knowledge/reindex` does it on demand. The lexical fallback `match_ai_knowledge_fts` ORs the meaningful words of the question (migration 064); before that it ANDed every word and natural questions matched nothing.
  - Prices: the catalog (`ai_attachments`) is the source of truth; the prompt tells the model to prefer it over KB excerpts when they disagree.
  - The web widget can book too (same booking tools as WhatsApp when hours are saved). It has no buttons, so `buildSystemPrompt({ bookingSlotButtons: false })` makes the model list the slots as text.
  - Handoff (`[[HANDOFF]]`): the customer always gets a goodbye (the model's sentence before the sentinel, else `HANDOFF_FAREWELL`). The owner gets an AI-written summary (`summarizeHandoff`, falling back to `buildHandoffSummary`) by Telegram and as an in-app `handoff_requested` notification for owners/admins (`notifyTeamOfHandoff` in `handoff-notify.ts`; migration 069, before it the type falls back to `conversation_assigned`).
  - "What do you offer?" lists every catalog name (also in the widget, which has no `send_attachment`); the model used to trim the list to fit the owner's short-message style.
  - Capture tools: `set_customer_name`, `add_note`, `set_custom_field` (only offered when the account has custom fields defined), `set_lead_stage` (only when `ai_configs.lead_pipeline_id` is set; it also carries the deal `value`/`currency`, persisted by `applyLeadCapture` in `custom-fields.ts`) and `set_sentiment`.
- **Clinic module** (module key `clinic`, migrations 066 and 067, `src/lib/clinic/`):
  - Doctors (`professionals`, with their own optional `hours`/`slot_minutes`) and `specialties`, linked through `professional_specialties`. `bookings.professional_id` is nullable. CRUD lives in `/api/clinic/{directory,specialties,professionals}` (admin only, 403 `module_disabled`, 503 `clinic_not_migrated` before the migration). The UI is Agenda → Doctores (`clinic-directory-dialog.tsx`, `useClinicDirectory`), plus a doctor picker in the booking form and a doctor filter on the agenda.
  - `getClinicDirectory` returns null unless the module is on, migration 066 has run and at least one doctor is active. While it's null, everything runs as the single shared agenda, so the module is inert by default.
  - Each doctor has their own agenda: their hours (or the business hours), their slot length, the business holidays and buffer, and only their own bookings count as busy. The `bookings_no_professional_overlap` exclusion constraint makes a double booking fail with `23P01`, which the AI reports as "already taken" and the bookings API as 409 `professional_busy`.
  - Agent: the prompt carries the roster with ids (`formatClinicRoster`). `find_professionals` searches by name or specialty, `check_availability` takes `professional_id`/`specialty` and tags each slot with its doctor, `book_appointment` requires `professional_id`, and `reschedule_appointment` can move to another doctor. Slot buttons add the doctor's name when the offer spans several doctors. The Telegram `check_free_slots` takes a `doctor` (name or specialty).
  - Migration 067 (`clinic-extra-panels.tsx`, tabs Servicios/Seguros, Ausencias inside a doctor) adds:
    - `professional_time_off` (business-local inclusive dates). `getClinicDirectory` loads the upcoming ranges, `dayWindow` returns null on those days, and the roster says "away …".
    - `clinic_services`, each with its own `duration_minutes`, optional price and specialty (null = any doctor). The service length sets the slot length (`DayWindow.durationMs`) while the doctor's slot length stays the grid step. `service_id` on `check_availability`/`book_appointment` only exists when there are services (`clinicSearchTool(directory)` returns `{ find, services, insurance }`), and it filters to the doctors of its specialty. Saved in `bookings.clinic_service_id`.
    - `accounts.clinic_settings` `{ ask_insurance, insurers }`. When `ask_insurance` is on, `book_appointment` requires `insurance` (saved in `bookings.insurance`). Before 067 the insert falls back to "Seguro: …" in the notes.
  - Manual bookings: `POST/PATCH /api/bookings` run `checkBookingSchedule` (holiday, then the doctor's time off/hours, or the business hours when there is no doctor) and answer 409 `outside_doctor_hours` with `reason` (`holiday`/`day_off`/`time_off`/`outside_hours`). The form then offers "Guardar de todos modos" (`force: true`).
  - Bookings with no doctor (made before the doctors existed) show a banner on the agenda, and the doctor filter has "Sin doctor" (`__none__`).
  - Reminders accept `{{doctor}}`, which is blank when the appointment has no doctor.
- **Booking reminders:** rules live in `booking_reminder_rules` (Agenda → Recordatorios; `{{reference}}` and `{{doctor}}` are available). The server drains due reminders every minute on its own (`startBookingReminderScheduler` in `src/lib/bookings/drain-reminders.ts`, started from `src/instrumentation.ts` in production only, since dev shares the production DB). `BOOKING_REMINDERS_INTERVAL` (seconds, `off` to disable) tunes it. `/api/bookings/reminders/cron` drains them on demand.
  - Migration 068 adds `kind` (`before` = reminder, `after` = follow-up, never sent to cancelled or no-show bookings) and `applies_to` (`all`/`appointment`/`table`/`event`). `ReminderRulesSettings` takes a `scope` and is mounted in the agenda, restaurant and events pages. Rules with `is_sample` never send until the owner presses "Usar esta regla".
- **Restaurant and events** (migration 068; page modules `restaurant` and `events`, feature module `waitlist`; all off until switched on):
  - `bookings.kind` is `appointment`/`table`/`event`. Table and event bookings never block the appointment agenda, and the agenda only lists appointments. References are `CITA-`/`RES-`/`EVT-` (`bookingReference(id, kind)`). `status` also accepts `no_show`, which frees the tables and the doctor's time.
  - Restaurant (`src/lib/restaurant/`, `/api/restaurant/*`, `/restaurant`): areas and tables (`min_party`..`max_party`, `combinable`), `booking_tables` with an exclusion constraint (23P01 = table taken) and a trigger that releases tables on cancel/no-show. `accounts.restaurant_settings`: duration 90 min by default, customizable per reservation between min/max; `allow_combine`, `max_party_ai`, `last_seating_minutes`, `allow_preorder` and its own `hours`. `pickTables` prefers the smallest single table and otherwise joins combinable tables of one area. Then the AI must ask the customer whether they mind sitting joined or at separate tables (`customer_agreed`, `seating`) before booking. Waitlist is `restaurant_waitlist`. Occupancy is `occupancyRate` in `tables.ts`.
  - Events (`src/lib/events/`, `/api/events/*`, `/events`): halls (capacity, price per hour, `min_hours`, setup/cleanup) and packages (fixed + per person). `accounts.event_settings` `{ requires_approval, deposit_required, deposit_percent, currency }`, each overridable per hall (NULL = inherit, `deposit_percent` 0 = no deposit). `event_status` pipeline: requested → quoted → deposit_paid → confirmed → completed | cancelled (`nextEventStatuses` skips the deposit step when there is none, and `initialEventStatus` follows the policy).
  - AI tools (`providers/venue-tools.ts`, wired through `src/lib/ai/venue.ts` in every channel): `check_table_availability`, `book_table`, `join_waitlist`, `check_event_availability` and `request_event`. Without executors (playground) they answer "Test mode". Telegram `check_free_tables` and `list_events` are read-only.
- **Sample data** (`src/lib/samples/seed.ts`, `/api/samples` `{ module: restaurant|events|clinic|reminders, scope? }`, `SampleDataBar`): every row created is `is_sample`, so "Quitar ejemplos" removes only those. Sample bookings get no reminders, Google Calendar sync or report counts. `preferReal` makes the AI ignore sample rows once a real row of that kind exists.
- **Deal closing** (migration 063, `src/lib/deals/`):
  - Won/Lost are real closes. `closeDeal` in `close.ts` sets `status`, `closed_at`, `lost_reason` and `close_note`, then moves the deal to the won/lost column. On a win it tags the contact "Cliente". Both outcomes fire the `deal_won`/`deal_lost` automation triggers, which carry post-sale and win-back messages.
  - Every close path uses it: the board and the deal form go through `POST /api/deals/[id]/status`, plus the AI's `set_lead_stage` and auto-lose.
  - Stages have `kind` (open/won/lost). Before the migration runs, `stageKind()` in `reasons.ts` falls back to the stage name.
  - Closed deals leave the board and appear in Embudos → Cerrados (`closed-deals.tsx`, filterable by date, status, reason and search).
  - A lost reason is required (`LOST_REASONS`, via `LostReasonDialog`).
  - The AI only advances an open deal. A returning customer gets a new one, and won/lost deals are never reopened.
  - `pipelines.auto_lose_days` (null = off) closes open deals with no message or change in that many days as lost (`no_response`), via `auto-lose.ts`.
- **Telegram owner assistant** (`ops-assistant.ts`, webhook `/api/telegram/webhook/[accountId]`): read-only. Its tools include `check_free_slots`, `list_new_contacts`, `sales_summary` and `search_business_info` (catalog + KB), with business-local date bounds. Enabling it (`/api/telegram/admin-chat`) registers the webhook at `NEXT_PUBLIC_APP_URL`, falling back to `NEXT_PUBLIC_SITE_URL` (the only one the Docker image bakes). The webhook only answers when `telegram_admin_chat_enabled`, the secret header matches `telegram_webhook_secret`, and the chat is `telegram_chat_id`.
- **Background jobs:** `src/lib/server-schedulers.ts`, started from `instrumentation.ts` in production. It drains automation Wait steps every 60s (`drain-pending.ts`, also behind `/api/automations/cron`), runs deal auto-lose hourly and checks the weekly summary every 15 min. Flows still need the external `/api/flows/cron`.
- **Modules:** every new capability must be a module the owner can switch on and off in Super admin → Módulos (`MODULE_KEYS` in `src/lib/modules.ts`; missing key = on).
  - Page modules gate their page with `useModuleGate`.
  - Feature modules (`ai_messages`, `telegram`, `widget_booking`, `google_calendar`) hide their UI with `isModuleEnabled(account.enabled_modules, …)`.
  - `telegram` is one switch for everything Telegram: handoff and lead alerts, the owner assistant webhook, the settings card and the weekly summary.
  - `widget_booking` adds the booking tools to the web widget on top of saved hours.
  - On the server, routes and jobs check `accountModuleEnabled` (`src/lib/modules-server.ts`).
- **Reports** (`/reports`, module key `reports`, `src/lib/reports/`, migration 065):
  - `computeOverview` in `overview.ts` is pure, and the loaders page past Supabase's 1000-row cap. It covers conversations handled by the AI alone vs with a person, response times (median/avg, AI vs human), the daily series, new contacts by channel (a contact's channel is its first conversation's), won deals by channel, "AI-assisted" revenue (the AI wrote to the contact before `closed_at`) and bookings (by the AI = `created_by` null).
  - **`messages.ai_generated` is the only "AI sent this" marker.** Every AI send path must set it: text, product cards/media (`engineSendMedia({ aiGenerated })`), slot buttons and widget replies. `senderKind` decides customer/ai/human/automation/system from it.
  - "Mensajes atendidos por la IA" (`ai-messages.ts`, `/api/reports/ai-messages`) lists AI replies with the customer message they answered. Ranges come from `range.ts` presets (business-local days).
  - Weekly summary: Telegram only, Mondays from 08:00 business time (`weekly-summary.ts`). `accounts.weekly_report_enabled`/`weekly_report_sent_at` are claimed with a conditional update before sending. It is toggled and sent on demand in Canales → Telegram, and only runs while the `telegram` module is on. WhatsApp would need an approved Meta template.
- **Google Calendar** (`src/lib/google-calendar/`, migration 065):
  - OAuth via `/api/integrations/google-calendar/{connect,callback,status,disconnect}`, with the dialog in Agenda → Google Calendar. "Conectar" opens Google in a popup (`?popup=1`, carried in the signed state): the callback answers with a page (`src/lib/google-calendar/popup.ts`) that posts the result through `window.opener` and a BroadcastChannel, then closes. A blocked popup falls back to the full-page redirect. It needs `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, and the redirect URI is `<base>/api/integrations/google-calendar/callback`.
  - The refresh token is encrypted in `google_calendar_connections` (RLS on, no policies, so it's service role only).
  - `syncBookingToGoogle(id)` mirrors a booking (insert/patch/delete, `bookings.google_event_id`). It is called from the AI's book/reschedule/cancel and the bookings API (`after()`), and is best-effort and never throws.
  - `googleBusy` merges the owner's busy events into `loadBusy` in `ai/booking.ts`. Events tagged `wacrmBookingId` are skipped.
- **Holidays:** `booking_settings.holidays` (dates) plus optional `holidayNames` (date → name; jsonb, no migration), edited in Agenda → Configuración (single day or range up to 60 days). They close the day for every doctor too. The agent sees them in the hours summary, `check_availability` adds `holiday` to its result, and `validateSlot` refuses them by name. The week view shades holidays and, when filtering by a doctor, their time off.
- **Agenda time:** the week view, the booking form and the page navigation use Santo Domingo days and times (`businessDate`/`businessTime`/`businessLocalToInstant`, weeks as ISO Mondays), never the browser's.
- **Agenda UI:** stat cards (`booking-stats.tsx`) and a filterable list view (`booking-list.tsx`) sit beside the week view. Date ranges come from `src/lib/bookings/ranges.ts` (business-local days). The dashboard shows `upcoming-bookings.tsx` when the agenda module is on.
- **Favicon:** `platform_settings.favicon_url` (migration 062), uploaded in Super admin → Branding. `src/app/icon.tsx` renders it, falling back to `logo_url`. It accepts PNG, JPG or SVG only, because satori can't decode WebP. The logo loader is shared in `src/lib/brand-icon.ts`.
- **PWA:**
  - `src/app/manifest.ts` (name from `platform_settings.company_name`, start `/dashboard`), install icons at `/pwa-icon/{192,512,maskable-192,maskable-512}` and `src/app/apple-icon.tsx`, all rendered from the brand logo.
  - `public/sw.js` is registered in production only (`ServiceWorkerRegister` in `layout.tsx`). It caches only `/_next/static` and shows `public/offline.html` when a page can't load. Pages, `/api` and other origins always go to the network. Bump `VERSION` in `sw.js` to drop old caches.
  - next.config serves `/sw.js` with no-cache.
- **Leads** (page module `leads`, `/leads`, migration 070): tab Oportunidades lists every deal (open/won/lost) with filters, summary and CSV; tab Formularios lists `lead_form_submissions`, the raw web-form payloads saved by `/api/leads/[key]/submit` (best-effort before 070).
- **Web Push** (feature module `web_push`, migration 071, `src/lib/push/send.ts`): handoff alerts also go as push notifications to owners/admins. Devices opt in on the Notificaciones page; iOS needs the installed app. Needs `VAPID_PUBLIC_KEY`/`VAPID_PRIVATE_KEY`/`VAPID_SUBJECT` (public key served by `/api/push/public-key`).
- **Chat colors (light mode):** outgoing bubbles are solid green `#1f7a52` with white text, the thread is `#f3f8f1`, and interactive buttons inside a bubble get their own dark ink (`.interactive-preview`) because the bubble re-points `--primary`.
- **Sizing:** the root `font-size` is 100% (16px, the browser default, and it follows the user's text-size setting). Every Tailwind size is rem-based, so this one value scales the whole app. Don't raise it to make things bigger.
- **WhatsApp:** the Cloud API never provides customer profile photos, so `contacts.avatar_url` is only filled by hand: `ContactPhotoEditor` in the inbox contact sidebar and in the contact detail sheet uploads it to the `chat-media` bucket. Render contacts with `ContactAvatar` (`src/components/contacts/contact-avatar.tsx`), which falls back to initials with a per-contact color. The CRMs that do show WhatsApp photos run on unofficial WhatsApp Web APIs, not the Cloud API. Inbound webhooks depend on the Meta app's callback URL pointing at this deployment, plus a valid `META_APP_SECRET`.
  - Read receipts and the typing indicator go through `engineMarkRead` (`src/lib/flows/meta-send.ts`). The auto-reply calls it before generating. The inbox calls `/api/whatsapp/read` when an agent opens a thread with unread messages, and while the agent types (throttled to once every 20s).
  - Meta gives no "customer is typing" event, so the inbox can't show one.
- **Web widget** (`public/widget.js`, plain ES5 with no build step):
  - Spanish only. Its look comes from `accounts.widget_config` (migration 060), normalized by `src/lib/widget/config.ts`, served by `GET /api/widget/[key]/config` and edited in Canales → Widget web → Apariencia.
  - Preview page: `/widget-preview.html?key=…`.
  - The visitor is asked their name after the first message, and the transcript is kept in localStorage.
- **Branding and color mode:**
  - Mode lives in `html[data-mode]` (light/dark; no attribute means dark), set by the boot script in `layout.tsx` and `use-theme.tsx`. Tailwind's `dark:` variant targets a `.dark` class that is never set, so those classes never apply; style per mode through the tokens in `globals.css`.
  - Light mode is a gray canvas (`--background`) with white cards and a soft card shadow, so surfaces don't blend into the page.
  - `platform_settings.logo_url` is the dark-mode logo, also used for the favicon. `logo_light_url` (migration 061, nullable) is the light-mode logo. Render logos with `BrandLogo` (`src/components/layout/brand-logo.tsx`): it outputs both images and CSS hides the wrong one, so there's no flash. Uploads happen in /super-admin → Marca.
- **Migrations:** the Supabase CLI here lacks privileges (`db push` fails with 403). New `supabase/migrations/*.sql` must be pasted into the Supabase SQL Editor by the owner, and code should tolerate the column being missing (`42703`) until then.
- **Inbox:** the colored dot on each conversation row is its status (open, pending or closed). It is not an unread marker, and the owner wants it kept that way. Unread is shown by the numeric badge.
- **Checks before committing:** `npx tsc --noEmit -p .`, `npx eslint src`, `npx vitest run`.
- **Deploy:** Dokploy builds from `main` with `docker-compose.yml`, which forwards only the variables it lists under `environment`. A new `process.env.X` needs its line there, or it stays undefined in production even when it's set in Dokploy. Commit only when asked.
